# 디자인 언어 SSOT — 데모 (v1.0)

> **이 문서는 공개 데모용 예시 데이터입니다.** 아래 서체·수치·조직명은 전부 가상이며, 실제 조직의
> 디자인 규칙이 아닙니다. 구조와 작성 방식(어떻게 하네스가 이 문서를 읽고 쓰는지)을 보여주기 위한
> 샘플입니다. 실제로 쓸 때는 각 팀의 확정 규칙과 측정값으로 이 문서를 다시 채우세요.
>
> 이 문서는 사람이 백지에서 쓰지 않습니다. 이미 만든 산출물을 스캔해서 "가장 많이 쓴 값"을
> 뽑아 초안을 채우고, 사람은 확인만 합니다. 정식 채움은 §9 인벤토리 스캔이 합니다.
>
> 상태: **`confirmed`** (데모) — 아래 규칙은 예시로 확정한 것으로 간주합니다.

## 확정 규칙 (예시)

```
1. 국문 서체            ExampleSans
2. 국문 자간            −1.5%   (영문 대문자 라벨은 미확립 — 판정하지 않음)
3. 600×400 예시 메시지   자간 가변 허용 — 판정 제외
4. 1080×1350 일반 게시물  좌우 72px
5. 1080×1350 표지·커버    좌우 112px
6. 1080×1350 광고        좌우 96px · 하단 240px 텍스트 금지 · 핵심은 중앙 1080×1080
7. 팀 D (예시)           별도 브랜드. 현 상태 유지, 판정 제외
```

**발효일** — 4·5·6번(좌마진·하단 금지영역)은 `spec.json`의 `effectiveFrom` 이후 만든 작업에만
적용합니다. 그 전 작업은 규칙이 없던 시절의 것이라 위반이 아닙니다.

## 3. 자간 — 한 줄 규칙 + 판정하지 않는 것

```
국문 텍스트          letter-spacing = −1.5%   (예시 샘플 교차 확인)
영문 대문자 라벨     미확립 — 판정하지 않는다
600×400 예시 메시지  가변 허용 — 판정 제외
```

> 영문 라벨을 판정하지 않는 이유(서사 예시) — 과거에 표본 1개로 수치를 확정했다가,
> 본문 영문이 전부 오탐으로 걸려 철회한 전례가 있다고 가정합니다. **근거 없는 것은
> 판정하지 않습니다.** 표본이 쌓이면 그때 정합니다.

## 3-1. 디자인 규칙과 검사 허용오차는 다른 것이다

| | 무엇인가 | 어디 있나 | 누가 쓰나 |
|---|---|---|---|
| **디자인 규칙** | 국문 자간 **−1.5%**. 새로 디자인할 때 맞추는 목표값 | 이 문서 · `spec.json` `tracking.ko` | 사람 |
| **검사 허용오차** | 기존 산출물을 훑을 때 얼마나 벗어나면 어떤 등급으로 보고할지 | `spec.json` `tracking.severity` | 스캐너 |

규칙을 느슨하게 만드는 것과 리포트를 현실적으로 만드는 것은 다른 일입니다. 후자만 합니다.

### 등급 — 빈틈 없음

| 등급 | 조건 | 뜻 |
|---|---|---|
| **PASS** | `t = −1.5%` | 규칙 준수 |
| **WARN** | `−2.5% ≤ t ≤ −0.5%` (−1.5% 제외) | 실무 편차 |
| **REVIEW** | `−3.5% < t < −2.5%` 또는 `−0.5% < t ≤ 0%` | 애매한 구간 |
| **FAIL 후보** | `t ≤ −3.5%` 또는 `t > 0%` | 강한 검토 대상 |
| **EXEMPT** | 600×400 예시 메시지 · 영문 대문자 라벨 | 기존 예외 |

### FAIL 은 수정 확정이 아니다 — confirmed-error 와 구분한다

| 용어 | 뜻 | 원본 수정 대상인가 |
|---|---|---|
| **FAIL** | 수치가 경계를 벗어남. high-priority inspection | 아니다 |
| **confirmed-error** | 실물을 보고 "실수다" 라고 확인된 것 | 그렇다 (승인 후) |
| **confirmed-intent** | 실물을 보고 "의도된 조판이다" 라고 확인된 것 | 아니다. 판정 제외 후보 |

**자간 수치만으로 원본 수정 대상을 자동 확정하지 않습니다.** 등급이 원본 수정을
승인하지 않습니다 — 실물 검증을 거칩니다.

### 관찰값과 추정값을 섞지 않는다

| 칸 | 내용 | 성격 |
|---|---|---|
| `observed` | 크기 · 자간 · 문구 · 문자 구성 · 노드 id | **사실.** 데이터에 그대로 있다 |
| `inferred` | 역할(제목/본문/캡션…) + `confidence` + `basis` | **추정.** |
| `verification` | 실물 확인 결과 | 확인 전까지 `pending` |

**추정을 사실 칸에 적으면 다음 사람이 그걸 근거로 원본을 고친다.** 그래서 칸을 나눕니다.

## 6-1. 작업 단위는 "프레임"이 아니라 캠페인 세트다

한 건의 작업은 낱장이 아니라 **주제 하나 → 채널별 산출물 묶음**입니다(예시 구조).

```
예시 캠페인 주제
├── 홈페이지·블로그 ▼     세로 상세 + 썸네일
├── PPT·줌배경 ▼          16:9 장표 + 줌 배경
└── 인스타그램 ▼          4:5 카드뉴스 세트
```

`palette` 스킬은 **세트 단위로 한 번** 배색을 정하고, 그 세트의 모든 채널이 상속받습니다.

## 9. 인벤토리 스캔 — 가이드를 사람이 안 쓰는 방법

**문제**: 디자인 가이드를 백지에서 쓰는 건 어렵습니다.
**해법**: 백지에서 쓰지 않습니다. 이미 만든 것에서 **빈도로 꺼냅니다.**

```
1  Figma MCP 로 전 페이지 순회 (get_metadata → get_design_context)
2  모든 프레임에서 수집: 규격 · 서체 · 크기 · 웨이트 · 행간 · 자간 · x/y · 색 · 이름
3  규격별로 묶어 빈도 집계
4  최빈값 = 사실상의 표준  → 이 문서의 템플릿 세트를 자동 생성
5  최빈값에서 벗어난 것    → 이탈 리포트 (수정 대상 목록)
6  사람은 "이게 표준 맞나요?" 목록에 O/X 만 한다
```

## 10. 변경 프로토콜 — 양방향 노티

확정 규칙은 **혼자 바꾸지 않습니다.** 한쪽이 바꾸면 다른 쪽이 모르고, 그게 갈라짐의 시작입니다.

| 신호 | 어떻게 알아채나 | 알릴 내용 |
|---|---|---|
| 새 기준값이 조용히 자리잡음 | 재스캔에서 최근 분기 최빈값이 확정 규칙과 다름 | "규칙을 바꿀까요, 작업을 맞출까요?" |
| 새 규격 등장 | 카탈로그에 없는 규격이 누적 | 규격 등록 제안 |
| 표준이 반반으로 갈라짐 | 최빈값이 2위를 1.5배 못 넘김 | "가변 허용"인지 확인 |
| 규칙이 현실과 싸움 | 같은 규칙에서 FAIL이 계속 쌓임 | 규칙을 고칠 후보로 보고 |

**판단 기준 하나** — 규칙이 손과 계속 싸우면 대개 **규칙이 틀린 것**입니다.
