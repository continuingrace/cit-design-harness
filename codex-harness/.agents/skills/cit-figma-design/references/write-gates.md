# Figma 쓰기 게이트

이 문서와 정책이 다르면 `config/harness-policy.json`이 우선한다.

## Staging 쓰기

대상 파일이 확정된 뒤에만 허용한다.

- `AI_CODEX__<작업명>`을 만들거나 그 파일을 쓴다.
- 기존 노드를 옮기거나·이름을 바꾸거나·대체하거나·삭제하지 않는다.
- 대상에 대해 활성 작성자를 하나만 유지한다.
- 쓰기 직후 스크린샷을 남긴다.

## 기존 원본 수정

쓰기 전에 아래를 제시한다.

- 파일명/키와 정확한 페이지/노드
- 계획된 작업
- 건드리지 않는 부분
- 보존 또는 되돌리기 방법
- 예상되는 눈에 보이는 결과

그 대상과 작업 범위에 대한 명시적 승인을 받은 뒤에만 진행한다. staging 승인은 원본 수정을 승인하지 않는다.

## 별도 승인이 필요한 작업

삭제, 기존 노드의 대체·이동·이름 변경, 컴포넌트·변수 변경, 라이브러리 publish는 각각 별도 승인이 필요하다. 어떤 도구가 승인받지 않은 작업을 부수 효과로 수행하려 하면 멈춘다.

## 검증

- 변경 전에 대상을 다시 읽는다.
- 변경 후 스크린샷을 남긴다.
- 결과를 승인된 범위, 변경 전 관찰 내용과 대조한다.
- 읽기 전용 감사를 실행한다. 감사에서 발견된 사항을 원본에 자동으로 고치지 않는다.

## 실패 시 복귀와 반복 제한

같은 게이트(승인 검증, Figma 쓰기, 검증 읽기)가 **같은 대상에서 두 번째로 실패**하면 세 번째 시도를 하지 않고 멈춘다. 멈춘 상태에서:

- 실패한 단계, 실패 원인, 시도 횟수를 작업 기록(`work/<작업명>/plan.md`)에 적는다.
- 대상을 승인 전 상태로 되돌릴 수 있는지 확인하고, 되돌렸다면 그 사실을 적는다. staging 파일이 아직 손상되지 않았다면 되돌릴 필요는 없다.
- 사용자에게 실패 내용과 함께 보고하고, 범위를 바꿔 다시 시도할지, 중단할지 판단을 받는다.

승인 서명을 반복해서 다시 받는 것으로 실패를 덮지 않는다. 범위나 대상이 바뀌지 않았는데 검증이 계속 실패하면, 그것은 재서명으로 고칠 문제가 아니라 멈추고 원인을 보고할 신호다.

## 중단 후 재개

작업이 중단된 상태로 다시 시작할 때는 `work/<작업명>/plan.md`의 기존 기록을 먼저 읽는다. 이미 쓴 노드, 이미 받은 승인, 이미 실패한 시도를 다시 만들거나 다시 요청하지 않는다. 승인 서명은 계획과 SSOT의 해시에 묶여 있으므로, 중단된 동안 SSOT나 계획이 바뀌었다면 이전 서명은 자동으로 무효가 된다 — 이는 오류가 아니라 설계대로 동작하는 것이며, 새로 서명을 받아야 한다.
